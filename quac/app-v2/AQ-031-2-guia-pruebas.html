Guía visual de pruebas: el aviso de teléfono autorizado espera unos minutos el nombre que el cliente le pone al teléfono

Api: testapi en feature/AQ-031-2 de api-quac-v2 (ya fusionada con release/4.1.0) · Tarea: feature/AQ-031-2 de api-crontab-v2 (Task142, cada minuto) · App 4.0.1: main (4.0.1+59, la de las tiendas) · App 4.1.0: release/4.1.0 de app-quac-v2 (4.1.0+60) · Las dos apps contra el mismo testapi · Datos de ejemplo: Martha, cédula de prueba 0000123456, celular terminado en 4567, teléfono «iPhone (iOS 26.6)», autorizado a las 10:00 a. m. con la espera en 5 minutos

Borde punteado = texto que arma el api o la tarea (la app no lo trae). Verde = lo que cambia con este REQ. Amarillo = lo que se toca.

Antes de empezar

  1. Testapi en la rama: en api-quac-v2, git fetch origin y git checkout feature/AQ-031-2. Ya trae release/4.1.0 (AQ-031, AQ-026, AQ-032 y el api de AQ-033). En quacapi_dev, el migracion.sql de AQ-031-2, bloque por bloque (corre el paso 1: debe dar 0 filas; no es idempotente; el paso 3 debe dar 2 filas del índice): 
    ALTER TABLE autorizaciones_dispositivo
  ADD COLUMN aviso_vence_at   DATETIME NULL COMMENT 'AQ-031-2: desde cuando se puede enviar el aviso',
  ADD COLUMN aviso_enviado_at DATETIME NULL COMMENT 'AQ-031-2: cuando se envio; NULL = pendiente',
  ADD INDEX idx_aviso_pendiente (aviso_enviado_at, aviso_vence_at);
  2. Crontab de pruebas: en api-crontab-v2, git fetch origin y git checkout feature/AQ-031-2. En su .env, WHATSAPP_TEMPLATE_AUTORIZADO_DISPOSITIVO con el mismo valor que tiene el api, y php artisan config:cache. Sin esa variable la tarea no manda el WhatsApp. Con php artisan tinker: config('app.timezone') debe dar America/Bogota y DB::connection('quac')->getDatabaseName() debe dar quacapi_dev. La Task142 corre cada minuto: el scheduler del ambiente de pruebas tiene que estar andando.
  3. Apps: 4.0.1: git checkout main en app-quac-v2. 4.1.0: git checkout release/4.1.0. Las dos con el env.json de testapi. La 4.0.1 no tiene «Renombrar»; la 4.1.0 sí.
  4. Encender y apagar la espera (se lee en cada autorización, sin caché y sin reiniciar; la espera queda fijada en la autorización: cambiar la variable no mueve los avisos ya pendientes): 
    -- encender, 5 minutos
INSERT INTO quacapi_dev.var_env (name, value, comments, created_at, updated_at)
VALUES ('AVISO_DISPOSITIVO_ESPERA_MIN','5','AQ-031-2',NOW(),NOW());
-- cambiar el valor (mayor a 30 = 30)
UPDATE quacapi_dev.var_env SET value='5' WHERE name='AVISO_DISPOSITIVO_ESPERA_MIN';
-- apagar: sin fila, vacía, 0 o un texto que no es número = el aviso sale al instante, como hoy
DELETE FROM quacapi_dev.var_env WHERE name='AVISO_DISPOSITIVO_ESPERA_MIN';
  5. Datos que hay que pedir (nunca clientes reales): una cédula de prueba con celular y correo a los que se tenga acceso, y una cuenta de prueba a la que le cambiaron el celular (fila en users_cupo_celular_historial con valor_anterior distinto de users.cupo_celular) para el caso 6. Cada caso arranca con una autorización nueva: un teléfono o emulador que la cuenta aún no tenga autorizado. Cada autorización manda SMS, WhatsApp y correo de verdad.
  6. Dónde ver el resultado: en la base quacapi_dev, tabla autorizaciones_dispositivo: aviso_vence_at (desde cuándo puede salir), aviso_enviado_at (cuándo salió; vacía = pendiente) y avisos_json (una entrada por canal). Cada caso trae su query de visto bueno de qa.md §5. El texto exacto de cada aviso se lee en el celular, en el WhatsApp y en el correo.
  7. Orden sugerido: caso 1 con la 4.1.0; caso 2 con las dos apps y, con la 4.1.0, dejar «Dispositivo autorizado» abierto para el caso 3 (mismo teléfono); caso 4 con la 4.1.0; casos 5 y 6 con las dos apps; caso 7 con solo SQL; al final, la regresión con la 4.0.1.
